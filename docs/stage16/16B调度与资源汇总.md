# 16B 调度与资源汇总

2026-11-12 · 以 16A 为基线。沿用 Worker 领取协议、现有数据库及设备预留事务。

## 领取顺序

节点先检查在线状态、槽位、Worker 版本和未完成回执。查询候选任务时，在数据库排除其他空间、指定给其他节点、训练器不支持，以及当前空闲设备无法满足的类型、显存和用途要求。该做法参考 [Kubernetes 调度器的可行节点过滤](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/#node-selection-in-kube-scheduler)，本平台仍由 Worker 主动领取。

每批读取最多 64 条，按优先级降序、创建时间升序、任务 ID 升序推进游标。继续读取直到派发一个任务或遍历完候选。设备授权、项目与资产、个人、组和全局额度仍在原事务中核验。设备与任务更新失败时保留原回滚处理。单批查询大小有上限，整次领取的耗时仍受匹配队列长度与锁竞争影响。

任务详情和领取复用节点就绪、设备规格与个人额度判断。保留现有原因代码；没有可用设备时，文字区分硬件或用途对应的设备、Worker 版本、节点离线或暂停，以及设备占用或槽位不足。该结果是即时诊断，不代表已预留或给出排队名次。

## 资源页

现有 `GET /api/v1/admin/nodes` 和 `GET /api/v1/workspaces/{workspace_id}/resources` 支持可选的 `include_summary=true`。开启后在列表的响应外层增加 `summary`；列表和分页字段保持原样。汇总独立于搜索、用途筛选和分页，分别覆盖全局管理范围或当前空间。工作空间原有资源查看权限保持，设备权限不因此扩大。

`summary.nodes` 含节点总数和在线节点数（已审核、未撤销、接收任务、心跳有效）；`summary.cpu`、`summary.cuda` 各含设备总数、占用、失联占用。总数按已审核、未撤销节点上的当前设备及仍有占用的消失设备计算。统计对象是已登记的逻辑资源，同一宿主上的多个 Worker 不据此算成多台物理主机。设备汇总统计占用，不替代按用户与任务计算的可调度设备。

资源页复用现有表格和标签组件。覆盖混合队列、跨批次跳过、同优先级顺序、两 Worker 竞争、失联回执、跨页汇总和空间隔离。浏览器以外的本地测试仍使用 D 盘隔离 SQLite；正式 PostgreSQL 并发和多物理机吞吐单独验收。
