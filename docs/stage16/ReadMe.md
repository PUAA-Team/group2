2026-11-11 · 16A 以 stage15 为实施基线。在线推理可配置专用设备，现有设备继续按共享处理。控制端采用 FastAPI 模块化单体，后台与 Worker 独立运行。当前使用本地 SQLite 验收，正式部署仍使用 PostgreSQL。

## 第一批：资源用途进调度

现在训练、评估、在线服务都走同一条 Worker 领取链路。调度检查设备类型、显存、训练器、授权和配额，但设备授权只有用户、组和启用状态，无法表达设备用于训练还是推理。长期运行的服务和训练因此可能竞争同一批资源。沿用现有设备策略和事务预留机制，在对应边界增加用途匹配。

代码入口：[设备策略](../../backend/src/model_platform/services/resource_policies.py)、[任务提交](../../backend/src/model_platform/services/jobs.py)、[Worker 领取](../../backend/src/model_platform/services/scheduler.py)、[设备策略接口](../../backend/src/model_platform/api/governance.py)。用途匹配抽成一处规则供提交、资源选项和领取复用。数据库事务继续负责状态变更和预留，API 层只做鉴权、参数处理和响应。

| 改动位置 | 拟改内容 |
| --- | --- |
| 设备策略 | 在现有 DevicePolicy 中加用途枚举「共享／训练评估／推理」。策略由管理员设置，默认共享，沿用已有修订号与审计。旧记录缺字段时按共享解读，存量授权及额度继续生效。具体 API 字段与兼容行为在开工前冻结 |
| 任务提交与领取 | 以任务类型决定所需用途。提交时检查指定节点或设备与用途是否冲突；排队期间的变更在 Worker 领取时重新核验。最终匹配还要检查工作空间、权限、配额、运行时、显存与占用。候选查询、原子预留和状态转换走同一条现有主链路 |
| 切换与恢复 | 设备有活动预留或失联待核查时拒绝修改用途。策略变更与领取沿用节点锁串行化。已运行任务与旧 Worker 继续使用原执行身份与回执协议。验收空间把设备显式分配给两类专用用途；工作空间统一禁用共享设备的开关另行评估。无合适设备时展示排队原因 |
| 页面 | 在管理员现有设备策略弹窗里加用途选项，在资源页展示用途标签。训练和服务创建页根据后端选项标记或排除不适用的资源；最终校验由服务端执行。复用现有云管控组件 |

共享设备仍可承接两类负载，指定为推理专用的设备从设置成功起便不接受新的训练或评估。设备隔离和并发隔离分开验证。现有全局、组与个人限额仍可能造成竞争，第一批区分能明确判断的等待原因。若验收场景要求训练满额时仍能发布推理服务，则单独设计可配置的推理容量预留，明确它与组和个人额度的关系。CPU 资源共用物理宿主时，设备用途仅保证逻辑分配，负载隔离还需独立宿主或资源限制与测量。

本地隔离验收覆盖旧策略、训练和推理用途、策略修改与领取竞争、无匹配资源、停止和失联预留。部署前补 PostgreSQL 并发、多物理机及推理延迟测量；使用相同模型和设备条件记录对照。旧代码不识别专用设备，回退期间需要暂停新派发。

## 后续顺序

| 批次 | 改什么 | 完成标志 |
| --- | --- | --- |
| Stage 16 第二批：调度与资源汇总 | 查询先过滤节点与设备硬条件，再按原优先级与创建顺序逐批读取。现有资源页显示全局或空间汇总，任务详情补等待原因 | 后排兼容任务可领取，保留占用和原执行回执。正式 PostgreSQL 并发和多物理机验收另行记录 |
| 下一批：文件存储与传输 | 先统一已存在的文件读写入口、版本引用和校验，默认服务器持久卷。沿用 Worker 摘要缓存，先测传输量与等待，再按需上报缓存可用性。阿里云 OSS 作为部署可选适配器，签发授权、校验、迁移和回滚另外走查 | 旧文件继续读取，训练输入与归档可核对。OSS 未配置时原流程能完整运行；启用后单独验收读写、授权和异常 |
| 演示批次：模拟算力 | 给演示空间加 Mock 节点和独立模拟执行通道，页面按资源和任务标注模拟；保留同一任务多卡规格 | 模拟八卡可走查匹配与预留。真实 Worker 领不到模拟任务，真实产物和实机统计不计模拟 |
| 按测量结果优化部署 | 先核对推理和监控负载；按需调整 Worker、副本、连接预算和后台进程。控制端按模块组织并同版发布 | 有同条件对照结果，部署和回退边界清楚 |
