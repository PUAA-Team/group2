# 16A 设备用途与推理隔离设计

2026-11-11 · 实施基线为 `20261101-15a`、数据库 `0011_console`。管理员可在资源页划分推理设备，训练、评估和部署服务执行同一套用途规则。

## 本批范围

| `purpose` | 界面名称 | 可分配任务 |
| --- | --- | --- |
| `shared` | 共享 | 训练、评估、在线服务 |
| `train_eval` | 训练与评估 | 训练、评估 |
| `inference` | 推理专用 | 在线服务 |

已配置的专用设备不能被另一类任务领取。共享设备仍能承接两类任务；要让某个工作空间完全隔离，可在演示空间将相关设备分别配置为两种专用用途。自动选择可落到共享设备，用户也可指定可见且兼容的节点。跨节点强制优先、工作空间统一禁用共享设备和推理并发预留均单独评估。组、个人和全局额度继续生效，设备用途不会提高原有权限或额度。

## 数据和接口

设备用途由管理端保存到现有 `DevicePolicy.value` 的 `purpose` 键，Worker 探测或上报不能修改用途。既有记录缺键、没有策略的设备和新接入设备均按 `shared` 解读。本批保持数据库 `0011_console`，不回填设备、任务或执行记录，不变更 Worker 领取和回执协议。

| 接口 | 契约 |
| --- | --- |
| `GET /api/v1/resources/devices/{device_id}/policy` | 返回生效的 `purpose`、现有授权字段与 `revision`。权限沿用资源策略接口。 |
| `POST /api/v1/resources/devices/{device_id}/policy` | 在既有请求上增加可选 `purpose` 枚举；字段省略时保留原值，显式 `shared` 才恢复共享。沿用管理员权限、CSRF 和 `revision`。非法枚举返回 422，旧版本写入返回 `412 REVISION_MISMATCH`。设备占用或失联待核查且尝试改用途时返回 `409 DEVICE_PURPOSE_IN_USE`。 |
| `GET /api/v1/workspaces/{workspace_id}/resources` | 每个设备增加 `purpose` 和面向当前用户的 `selectable`，授权名单仅在策略接口返回。支持按 `job_kind`、`device_kind` 筛节点后分页；兼容但暂忙或离线的节点可选。列表与选择结果反映配置，领取时重新检查可用性。 |
| `POST /api/v1/workspaces/{workspace_id}/jobs/{job_id}/submit` | 自动选设备仍可提交等待。指定节点时验证节点归属及已知用途；同设备类型的已知设备全部因用途不匹配而不可选时返回 `409 DEVICE_PURPOSE_MISMATCH`，保留草稿。暂忙、暂离线或硬件类型不同不按用途错误处理。无权查看的节点与不存在的节点使用相同响应。 |
| `GET /api/v1/workspaces/{workspace_id}/jobs/{job_id}` | 保留 `queue_reason` 中文文字，增加 `queue_reason_code`：`no_matching_purpose`、`no_available_device`、`quota_full`、`project_archived`、`worker_upgrade_required`、`waiting`。任务离开队列后两字段为 `null`。提交响应也返回同样的诊断。诊断按提交者权限执行，只读且不暴露额度明细。 |

保存用途继续使用设备策略的版本控制，并记录修改前后用途和操作人。存量草稿无新增必填字段；历史任务不补写用途和调度事实。队列里指定节点的任务如果因策略变更失去匹配，保持排队，给出等待原因，用户可取消后用合适节点重新提交。

## 调度与并发边界

1. 在设备策略模块集中定义「任务类型能否使用设备用途」；资源选项、提交预检、Worker 领取共用。训练 `train` 与评估 `evaluate` 统一匹配 `train_eval` 或 `shared`，服务 `service` 匹配 `inference` 或 `shared`。
2. 设备策略修改与 Worker 领取共用节点锁。获取锁后刷新设备占用和策略；用途发生变化且设备存在活动预留时拒绝。执行失联但占用尚未结案时同样拒绝。修改授权的旧行为沿用已有策略，生效用途没有改变时不触发新的用途检查。
3. 领取时重新核验任务类型、设备授权、当前用途、运行时、显存和额度，继续在同一事务内写任务状态、执行身份和预留。已有执行回执、停止、重投递与失联核查沿用原协议。16B 再处理候选截断和队列扫描，避免把两类调度改动放进同一发布。

管理员在「资源管理 → 计算节点 → 设备清单 → 配置策略」的弹窗调整设备用途，列表用短标签标识用途。训练向导、创建评估和部署服务复用同一资源选项，按任务类型和 CPU/GPU 过滤。已有草稿里的旧节点若失去兼容性，会标成「不可选」并保留原值，便于用户主动改选；提交仍由后端核验。

## 实施与验收顺序

| 步骤 | 工作 | 通过条件 |
| --- | --- | --- |
| 1. 后端规则 | 策略读写、设备响应、选项过滤、提交预检和领取复核 | 共享兼容，训练/评估和推理互不串用；旧请求省略用途不覆盖新配置；旧策略保持原授权。 |
| 2. 控制台 | 设备授权弹窗、用途标签、训练与部署选项、排队反馈 | 管理员可完成配置，普通成员不能修改。配置后前端与直接 API 提交结果一致。 |
| 3. 本地隔离验收 | 隔离 SQLite、API 和前端测试 | 覆盖用途与领取竞争、失联占用、反向指定节点、额度与旧请求兼容。 |
| 4. 部署前复核 | 独立 PostgreSQL 和真实训练 Worker | 重跑竞争和回执流程；多物理机、GPU 与时延按可用环境单独记录。 |

本批复用现有依赖。在本地运行轻量测试；真实 GPU、外部模型调用和发布需要相应运行环境。

## 发布与回退

隔离验收通过后，整理 OpenAPI、验收截图、测试摘要及上线差异，提交审阅。上线使用现有 Compose 发布方式；先核对在途执行及后台工作，再在服务器保留备份。采用新版本后先查登录、资源和任务，再按获准的空间设置设备用途。旧版本读取新 JSON 时不会执行用途限制，且旧写入可能覆盖新字段；回退前暂停新领取、策略写入和相关后台写入，优先用经验证的兼容镜像。回退不覆盖数据库或删除新任务；如有在途任务，先按可用的兼容路径保留回执和执行记录。
