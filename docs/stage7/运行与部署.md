# 资源运行与部署

控制端沿用 D 盘 backend-runtime，Worker 状态、缓存、日志与训练环境全部在 D 盘英文目录。安装依赖只发生在用户批准的 worker-llm-runtime 及后端隔离环境。当前真实入口为 `http://127.0.0.1:8000/`，原型 8765 保留。

本机使用原生 Python Worker 验证；远程部署提供 PowerShell/shell 命令与 Dockerfile。主服务和 Worker 分开运行，远程 Worker 主动访问主服务器，无需 Worker 入站端口。当前主服务仍只监听回环，多机时需要配置可达的控制端地址及 HTTPS/局域网监听。

## 本机操作

进入“资源管理”或“资源监控”。本机已接入 RTX4060，选择“计算节点”可查看心跳、硬件和运行时。节点详情可配置、重新探测、暂停接收和撤销；暂停不终止现有任务，撤销要求设备空闲。利用率未知显示横线，失联仍占用的设备继续保留。

管理员点击“接入本机”，选择工作空间和 PyTorch + Qwen LoRA 环境。首次注册自动审核；其他机器由接入申请决定是否自动审核。停止本机 Worker 前先停止它的训练和服务；确认停止回执后再关主服务。不能通过关闭网页来停止 Worker。

项目根目录重启控制端：

```powershell
& .\backend\scripts\run_backend.ps1 -BackendAction serve -EnableLocalWorker
```

该命令为前台运行，Ctrl+C 停止此控制端进程。本机已完成初始化，不需要开启浏览器首次设置。后台当前进程记录在 `D:/model-training-demo/backend-runtime/backend-process.json`，仅停止已核对的项目进程。不要重复启动8000。

Worker 日志位于 `D:/model-training-demo/backend-runtime/local-worker/worker.out.log` 和 `worker.err.log`。每次执行位于其 `executions/{execution_id}`，包含 spec、events、result、process.log；目录还含私有节点凭据，不打包公开。缓存可保留用于复用；运行期间不删除工作目录。

## 连接其他电脑

1. 主服务部署在对方能访问的局域网地址或 Linux HTTPS 域名。当前127.0.0.1仅用于本机，不能填写到另一台电脑的接入命令。
2. 在资源页面选择“生成接入命令”，填写主服务器地址、Worker工作目录、训练Python及平台。Windows工作目录放空闲磁盘，例如D盘；Linux可以使用用户目录。
3. 复制命令，在目标机器执行。命令下载固定版本Worker、校验SHA256，以标准输入传入十分钟接入码。页面显示掩码，完整命令只在本次复制内容中；不要公开转发。
4. Worker主动注册、发送硬件和运行时。未自动准入时由管理员在节点配置勾选审核。批准后才可领取该空间任务。

目标机器已有兼容PyTorch时直接使用对应Python；只做硬件接入时可以使用标准Python，但运行时未就绪将不能执行训练。完整三路线环境使用 `worker/requirements-llm.txt`。GPU还需兼容的NVIDIA驱动。安装和驱动调整应由机器所有者执行，本轮没有替其他电脑安装环境。

Qwen基础权重需先缓存固定提交。仓库脚本 `scripts/fetch_qwen_model.py --root D:/model-training-demo/worker-llm-runtime` 对应HF_HOME为该目录的 `cache/huggingface`。远程机器可复制已核对的完整缓存目录，或按同一公开提交下载；启动Worker时增加 `--model-cache` 指向HF_HOME目录。用户数据和LoRA产物由主服务器经执行鉴权传输，Worker校验哈希并缓存。

## 容器交付

提供 `worker/Dockerfile` 和 `.dockerignore`。在具备Docker与NVIDIA Container Toolkit的Linux主机上，以worker目录为构建上下文：

```sh
docker build -t registry.example.com/team/training-worker:0.1 worker
docker push registry.example.com/team/training-worker:0.1
```

镜像地址替换为团队实际仓库。基础镜像为PyTorch2.5.1/CUDA12.1的候选配置，也可通过WORKER_BASE_IMAGE指定已核对镜像；构建时应核对镜像标签和基础环境。资源页面的Docker方式填写已构建并可拉取的镜像，生成mkdir、docker pull和带GPU/工作目录挂载的启动命令。首版命令在前台运行，需由团队安排进程托管。凭据与缓存通过/state持久化。

本机没有Docker；镜像构建、Linux、多机网络和PostgreSQL尚未验收。容器文件与命令已提供，真实运行证据为Windows原生Worker。

## 备份与恢复

本轮应用库迁移前备份：`D:/model-training-demo/backend-runtime/backups/pre-compute-jobs-20261029-003421/platform.sqlite3`。迁移0002_compute、0003_jobs只新增资源、任务、执行、调用与密钥相关表，升级后核对原表行数一致。代码备份位于stage7-20261028。

恢复时先通过页面停止任务、服务和Worker，再停止控制端，另存当前数据库与storage，最后成套恢复对应代码、数据库和文件版本。已经产生新数据时不直接覆盖为旧库。原备份不包含之后的预置和训练产物；权限配置前另有pre-demo-policy备份，见 `local-demo.json`。
