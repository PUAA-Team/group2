2026-10-31已发布`20261031-13b5b`，缓存`stage13-5b`，数据库`0009_audit`。[进入平台](https://47.93.115.188:5488/?deployment=stage13-5b#/home)。原账号、资产、任务和节点记录保留，本机GPU节点继续暂停。当前接口见[OpenAPI](./openapi-b5b.json)。

## 页面使用

在“资源管理”进入节点详情，可以切换设备与近1小时、6小时、24小时或7天的利用率、内存记录。每30秒最多采一条，保留7天，查询最多返回240个点；缺失值和时间空档保持断线，历史数据不补造。CPU和内存来自所在主机；容器独立限额统计后续补充。

管理员通过设备“授权”弹窗配置允许或禁止的用户、用户组。显式禁止优先，未设置名单时沿用空间权限。暂停节点仍然暂停，不因修改授权恢复。节点详情另提供Worker下载与升级状态。

“用户管理 → 用户组 → 共享预算”维护组内GPU、并发和文件存储总额。留空表示未另设上限，0表示禁止新增对应占用。个人继承额度继续生效，组共享预算独立限制合计使用。执行领取时固定计入组，之后换组不会搬移原占用。

“用户空间”展示实际文件用量，按数据版本、模型产物和处理候选分类。计量包含每份实际保存的对象文件，归档后继续计量；远端基础模型引用、Worker缓存和数据库另行管理。旧文件的创建人优先从已有审计恢复，历史组归属保持未知。新上传和产物回传先检查个人及组剩余空间，超额明确拒绝。

模型和数据集详情支持弹窗归档、恢复。归档关闭新版本、新处理和新训练入口，服务端同样复核，排队任务领取前也会检查；已运行任务与历史下载保留。

任务详情提供“执行核查”，管理员先暂停节点，检查目标机器进程已经结束，再填写原因并明确勾选确认，才能结为失败或停止。在线节点仍上报执行时拒绝人工释放。迟到回执不能覆盖人工结案，未知运行情况不会自动释放设备。上线时未对生产中的任何历史执行执行人工结案。

管理员作业页新增“数据处理”和“智能请求”标签。只查询状态、空间、创建人、时间、类型、错误码及已报告Token等元数据，不返回外发内容或真实样本。统计页新增实际文件字节、已结束GPU预留时长、智能请求及失败阶段；预留时长按领取到结束计量。操作记录可筛选失败写操作，查看错误码与请求编号，不保存请求正文或完整错误详情。

云端CPU容器实际完成两版TinyCNN训练、同一图像版本评估、错误图片读取及一次图像推理。验证集故意给同一图片配相反标签，用于稳定检查错误定位，不能用这组准确率评价模型质量。新版Worker另外完成文本分类训练、权重上传与下载，报告执行契约版本1。此前双容器文本流程见[B5a](./B5a运行与验收.md)。所有容器共用一台ECS，未宣称为多台物理机验收。

故障注入只修改隔离合成数据：组存储设为0后，真实训练产物被拒绝上传，Worker记录artifact_upload失败、保留本地文件，并在子进程退出后释放设备；另一任务在领取前损坏输入，记录input_transfer失败，没有启动训练子进程。原文件和预算随后恢复。

PostgreSQL验证历史实际文件账目及创建人恢复；两个协议节点竞争共享并发1只有一条领取；剩余空间仅够一份文件时并发上传结果为成功与超额各一；31条待处理调用再并发提交两条，只接收一条；同一密钥并发轮换只有一次成功。节点竞争使用协议夹具，文件额度边界使用明确元数据夹具，不冒充这些部分实际执行了训练或写满1GiB。

验收脚本曾两次误读接口字段，分别把数据集名称写为dataset_name、把inventory.runtime写为runtime，均在脚本断言处停止；按实际接口修正后重跑通过。最终镜像测试未因此修改应用。保留既有Starlette/HTTPX测试适配弃用提示，没有新增依赖消除提示。

## Worker升级

本批新任务需要Worker上报`execution_contract_version=1`，旧Worker保持原回执路径，升级前不会领取新任务。当前本机资源暂停要求继续有效，本轮没有替换或启动本机Worker。

恢复使用时按以下顺序操作：

1. 管理员保持节点暂停接收，检查训练与服务已经结束，并在Worker机器确认没有对应子进程。存在不确定执行时先核查，不直接删除状态文件。
2. 协作停止Worker，保留完整状态目录、凭据和执行日志；把原worker.pyz复制为带日期的备份。
3. 从已登录平台“资源管理 → 节点详情 → 下载Worker”获取新worker.pyz，替换该程序文件。下载接口为`GET /api/worker/v1/bundle`。
4. 使用原控制端地址、state-dir、trainer-python、model-cache和槽位配置启动。云端接入过的本机命令仍见[stage12](../stage12/运行与验收.md#本机worker)，不要重新注册或创建第二个身份。
5. 节点页面确认Worker状态为“已就绪”、设备和运行时正确，再由使用者恢复接收，先提交一个短任务检查产物和资源释放。

启动失败时停止新进程，恢复备份的程序文件并保留原状态目录；旧版只能处理其既有执行，不能领取本批新任务。不得同时运行两个共用同一状态目录的Worker。

## 部署和回退

服务器停写后备份在`/srv/model-platform/backups/pre-stage13-b5b-20261031`，包含数据库、storage和受限配置，权限限制且只留服务器。准备及发布代码为`scripts/deploy_stage13_b5b.py`。发布前所有生产执行结束，api与operations停止后才备份、执行schema8/9迁移和切换current；发布后核对原记录集合保留。

只读兼容版本为`/srv/model-platform/releases/20261031-13b5a-compat09`，已验证识别schema9、查询健康及写请求返回503。旧业务写入路径不了解新授权、预算和归档约束，因此应急回退按以下方式进行，operations保持停止：

```bash
cd /srv/model-platform/current/deploy/server
docker compose --env-file .env stop operations api
ln -s /srv/model-platform/releases/20261031-13b5a-compat09 /srv/model-platform/current-rollback
mv -Tf /srv/model-platform/current-rollback /srv/model-platform/current
cd /srv/model-platform/current/deploy/server
docker compose --env-file .env up -d --no-deps api
docker compose --env-file .env exec -T gateway nginx -s reload
```

切换前确认没有在途执行。回退保留新表和记录，不恢复旧数据库覆盖新增数据。正常前进修复后再启用operations。schema9独立于已验证的schema8迁移新增失败审计字段，没有修改已存在迁移的业务含义。
