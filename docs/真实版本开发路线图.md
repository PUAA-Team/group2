# 大模型集成训练平台开发路线图

2026-11-11 · 计划。以 stage15 发布及验收记录为基线。采用模块化控制端，微服务保留在架构选型比较中。先把一期真实业务、资源隔离和恢复做完整。阶段编号为实施顺序，后续可选项单独排期。

## 当前架构选择

**近期采用模块化控制端、独立后台和独立 Worker。** FastAPI API 与 operations 已分进程运行，同版发布，共用 PostgreSQL 和文件目录。Worker 通过既有协议接入。下一轮先理顺代码里的依赖和数据写入责任。训练提交、调度、设备预留与额度核验仍由同一控制端协调，保留领取事务和失败处理。

| 边界 | 近期实现 | 后续优化条件 |
| --- | --- | --- |
| 训练任务与资源调度 | 持久队列和 PostgreSQL 事务。任务状态、有效执行、设备预留与额度在同一控制边界内裁决 | 优先改进排队、锁竞争和查询。若采用专用调度进程，先证明既有领取接口和事务边界仍成立 |
| 推理 | 运行时留在 Worker；控制端负责服务登记、授权、调用记录与状态。16A 增加专用设备用途 | 先按模型和负载扩充推理 Worker；有测量证据再优化流量入口和请求队列，沿用控制端鉴权与审计契约 |
| 监控与日志 | 延续事件回报和页面刷新。先补批量写入、保留策略、游标和负载观测 | 指标和日志经过批量写入、限流及查询优化后，仍持续占用连接或 I/O，并影响任务受理。优先独立采集与查询进程，任务终态仍由控制端确认 |
| 数据处理与智能辅助 | 继续使用后台执行。区分两类任务的超时、并发预算和失败路径 | 若外部模型慢请求或大数据处理造成明显互相阻塞，先拆为两个可独立配置的后台进程，分别观察排队和失败率 |

优化先对照同一环境的吞吐、P95、错误率和资源消耗，区分设备、进程、数据库与网络瓶颈。独立后台进程继续同版发布；新增独立进程前，明确职责、超时、重复处理、升级兼容及回退，再用相同场景验证收益。只有实际需求超出现有部署边界时才重新评审架构选型。

## 开源平台对照与调整

[Crater 的架构](https://github.com/raids-lab/crater)把账户、配额、任务、服务与资产放在控制端，Kubernetes 和 Volcano 负责执行与调度。它的[实验室队列](https://raids-lab.github.io/crater/en/docs/admin/deployment/volcano/)把每个实验室的容量、优先级和共享策略落实到实际调度。项目已有工作空间、用户组配额、设备授权和事务预留；近期优先补设备用途、等待原因和资源利用率。继续让本地 CPU、远端笔记本和 Linux GPU 主机通过独立 Worker 接入，按能力与协议版本匹配。若以后有由团队统一运维的 Linux GPU 集群，需要拓扑感知或成组调度，再评审 Kubernetes 执行适配器，保留同一套上层任务语义。

| 参考 | 在项目中怎样落地 |
| --- | --- |
| [Kueue：配额准入与队列策略](https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#queueing-strategy) | 区分配额是否允许、有没有匹配设备、执行是否已启动。当前领取先取工作空间队首 200 条，再判断训练器、设备和配额；前 200 条均不匹配时，后面的可运行任务可能始终选不到。16B 将可索引的硬条件前移，剩余动态条件用有界扫描处理，并测试后排兼容任务能被领取；排序和最终事务核验保留。 |
| [Kubeflow Trainer：训练运行时模板](https://trainer.kubeflow.org/en/latest/operator-guides/runtime.html) | 已有任务快照固定模型、数据版本、训练器标识与参数，Worker 已上报运行时能力。扩展训练器前补受控的运行时版本、依赖和设备要求，并记录每次实际执行环境。资产登记、参数模板和运行环境分别维护；管理员新增资产时仍从已支持的训练器中选择。 |
| [MLflow：元数据与产物分存](https://mlflow.org/docs/latest/self-hosting/architecture/overview/) | 延续 PostgreSQL 存版本与引用、文件层存数据与权重。Crater 的[存储设计](https://raids-lab.github.io/crater/en/docs/admin/deployment/storage/)还区分节点本地与共享存储。本项目先统一服务器持久卷和 Worker 摘要缓存的文件契约；明确现有 Worker 通用传输的 64 MiB 限制，按支持的文件规模验证流式校验与传输。OSS 按部署启用，缓存调度根据实测流量和等待时间决定。 |
| [Airflow：控制端与远端执行边界](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html#task-execution-architecture) | 保持 Worker 通过执行 API 领取任务、回报事件，数据库只由控制端写入。优先记录准备、运行、回传各段耗时，验证重投递和断网回执。控制端先按实际负载优化接口与后台进程，再决定是否引入独立服务。 |

推理先落实专用设备与就绪检查，再分别测发布等待、模型预热、请求排队和执行延迟。服务已有就绪状态，验收应覆盖训练满额时的发布与已就绪服务的调用。若空闲推理设备仍被并发配额挡住，单独评审推理容量预留，并明确它与全局、组及个人上限的关系。

## 实施批次

| 阶段 | 主要开发工作 | 交付和退出条件 |
| --- | --- | --- |
| **16A 推理资源隔离** | 复用设备策略，增加共享、训练评估、推理专用三种用途。统一资源选项、提交和 Worker 领取规则。后台核验设备授权、用途与额度，保留原子预留。现有管理弹窗加用途字段，训练和服务页面显示可用资源与等待原因 | 旧设备按共享解读，已有服务和 Worker 可继续运行。两个用途并发不串用，策略修改与领取并发无重复预留。用专用设备跑通训练与推理。若全局或用户配额仍导致推理无法发布，按实际需求单独设计容量预留 |
| **16B 调度可靠性与资源观测** | 分清资格判断、状态事务、API 三层责任。调整候选筛选顺序和扫描边界，补节点/设备汇总、类型筛选、容器 cgroup 指标及排队原因。排队优先级保留授权与审计。走查重领、断网、停止、后台重启和未知执行核查 | PostgreSQL 并发验证通过；CPU 不受队首大量 GPU 任务阻塞，匹配任务仍按优先级和提交时间领取。任务等待可解释，失联不会误释放设备。跨独立主机并行需要实机证据，同宿主容器作为并发验证 |
| **17A 文件与资产边界** | 先盘点已有文件引用，再统一读、写、校验与归档入口。默认服务器持久卷，Worker 本地摘要缓存。记录传输量和准备时间。受控权重导入另定格式、来源、训练器兼容及发布条件 | 旧文件和资产版本继续可读，训练、评估、推理均复用已校验版本，摘要和引用一致。关闭 OSS 的部署能完整运行 |
| **17B 可选 OSS 与缓存调度** | 用同一文件契约接入可选阿里云 OSS。支持短时授权、按实际需求分片续传和异常清理。已有文件先迁移、校验再切换。缓存调度先做设备硬过滤，再在匹配节点间比较缓存命中与传输代价 | 私有对象授权、续传、失败回退、已发布版本与旧任务复用通过。记录公网流量和回源次数。缓存优化经同条件对照后启用 |
| **18 一期补齐与验收** | 补工作台待处理、个人任务、统计成员/时段、标签分布和校验报告。验证文本分类、图像分类、Qwen LoRA 的训练、评估、推理闭环。三项智能辅助检查授权、预览确认和人工采纳，图像标注单独验证视觉连接 | 用户可从页面完成关键链路，状态、结果和日志可见。CPU、CUDA、真实视觉调用各按实际资源记录结果。按隔离条件完成负载、断网和服务器内恢复演练。异地恢复需独立备份位置与授权 |
| **19 可选演示与平台扩展** | Mock 八卡先做独立模拟通道和资源标识。新增真实训练器、同任务多卡、多机训练各自立项，明确设备拓扑、成组预留、失败恢复和运行时支持 | 模拟任务只在模拟队列运行，实机 Worker、配额、模型登记与统计均隔离。真实多卡和多机能力须分别取得实机证据 |
| **后续：Agents** | 先做明确的工具契约与工作空间权限，支持只读查询、日志解释和参数建议。新任务配置或数据版本由用户确认后创建。记忆与新增工具按需扩展 | Agent 调用可审计，权限和人工确认贯穿流程 |

主要依赖是 **16A → 16B → 17A → 18 的默认部署验收**。17B 从 17A 的文件契约开始，可按对象存储需求单独推进。控制台补齐可与文件边界并行，Mock 依赖稳定的调度契约。阶段 18 的默认部署以服务器磁盘为基线，可选 OSS 的验收单列。

## 分批开发清单

### 16A：能从页面配置和验证推理隔离

[首批设计与验收](./stage16/16A设备用途与验收设计.md)将这一批拆为：后端规则与兼容、前端操作、隔离数据库竞争验证、浏览器演示。可直接验收「划设备 → 训练 → 评估 → 发布 → 调用 → 停止」。管理员在已有弹窗配置用途，后端负责最终匹配。上线前明确旧版本回退时如何阻止它领取专用设备。组与个人额度规则保持，按用途划设备后的并发预算另测。

### 16B：调度可靠、资源看得清

1. **16B.1 候选与事务。** 用带 200 条以上待办的隔离库复现队首问题，再把设备类型、明确指定节点等可索引条件放到候选查询前。有界扫描仍不能让不合格队首无限挡住后排；匹配任务保留优先级和提交时间排序。最终授权、额度、状态及设备占用继续在 PostgreSQL 内原子核验。记录数据库扫描数量、领取耗时及锁等待；不将队列迁往新的中间件。
2. **16B.2 等待与治理。** 任务详情区分未找到兼容设备、设备忙、节点离线、额度不足和等待派发；来源变化时刷新原因，无法确定时保持通用等待。排队优先级调整只开放给获授权角色，带修订号、审计及状态限制。用多工作空间验证不能读到他人的任务、节点或额度。
3. **16B.3 资源观测与恢复。** 资源页增加设备类型、用途、健康和占用汇总。Linux 容器区分 cgroup 限额与物理宿主指标；同宿主多 Worker 的设备和容量不能重复计数，无法辨认宿主归属时分列展示。验证断网续报、停止与完成竞争、控制端重启，以及失联占用由谁解除。先做云端同宿主竞争回归，再在有授权的独立机器上补实机证据。

### 17A：先把默认文件路径做稳

盘点上传、预览、训练、评估、发布与归档读取的文件引用，建立一个可兼容旧键的读写入口。数据和模型版本保留原 ID、摘要及归属；文件校验通过才登记或替换引用。统一流式传输、大小限制、空间配额、失败清理和重复上传行为，先测现有通用 64 MiB 路径，再决定逐类提升的上限。对照冷缓存和热缓存记录实际传输字节、准备耗时、命中与回源。受控权重导入单列：先明确来源和训练器兼容，仅接受允许格式；解析失败不进入模型仓库的可用版本。

### 17B：按需求启用可选存储

先接私有 OSS、短时授权及校验，再按目标文件规模补分片恢复和异常清理。迁移先复制并核验清单，再切换读写引用；失败保留默认磁盘方案，禁止用新空桶覆盖旧数据引用。缓存调度只在已匹配设备之间比较，不突破权限、显存、额度或优先级。开启实际流量前需要桶、预算及可验证的配置，默认部署可单独验收。

### 18：补齐页面并完成一期验收

| 批次 | 功能与证据 |
| --- | --- |
| 18A 控制台补齐 | 增加工作台待处理和个人任务、统计成员/时段维度、数据标签分布和校验报告。按现有云管控样式复用组件；权限、空状态、失败状态和导出同步验收。 |
| 18B 真正业务闭环 | 用固定模型、数据版本和运行环境验证文本分类、图像分类和 Qwen LoRA。每条都从页面训练、评估、发布、调用、停止；验证 Qwen 分类合法标签约束。三项智能辅助核对预览、外发确认和人工采纳，视觉连接单独验证。 |
| 18C 稳定性和发布 | 在同一环境记录提交、列表和推理时延，注入 Worker 断网、执行中重启、重复回执、文件损坏与供应商超时。走一次服务器内恢复，报告实测 RPO/RTO；整机回收与异地恢复单列。 |

18A 可与 17A 并行。18B 的新 GPU 回归、多物理机和视觉供应商分别依赖可用资源与授权；缺条件的场景继续标记待验。真实生产外发默认状态不因测试改变。

### 19 及以后：模拟、多卡与 Agent

优先实现八卡 Mock 的独立模拟入口，验证资源、事件、产物和统计隔离。真实多卡任务另行设计运行时、拓扑、成组预留、屏障和失败恢复；先验同机多卡，再评估跨机。Agent 先封装只读的任务、日志、资产与资源工具，再开放参数建议和生成草案；写操作走既有授权与人工确认。记忆后加，定义工作空间隔离、保留期、可查看和可删除。每类扩展分别立项，不阻塞一期主链路。

## 每批交付顺序

先锁定设计、API、数据兼容和验收场景，再按「后端规则 → 前端操作 → 本地隔离验证 → 提交」推进。新接口同步导出 OpenAPI，运行说明记录验收与回退，文档索引随批更新。阶段测试通过后提交到独立开发分支，主分支暂不合并。新服务器就绪后安排正式环境验收与发布。

## 发布门槛

- **业务闭环。** 以版本化数据与模型提交任务，能看到排队、训练日志与指标、评估、归档、发布、调用和停止。现有账号、资产、历史任务和 Worker 兼容。新 API、数据库变更、前端入口、错误和权限一并验收。
- **测量。** 沿用架构目标的初始负载（20 个活跃会话、3 个在线 Worker）。对照任务受理 P95 ≤ 1 秒、任务列表 P95 ≤ 500 ms、失联检测 ≤ 60 秒、同条件推理 P95 退化 ≤ 20%。文件传输、资源等待和模型预热分别计时，报告设备、工作负载和实验条件。目标与实测分列。
- **恢复。** 核查重复领取、失联、任务执行期间重启及结果回传。隔离环境验证数据库和文件一致恢复，参考 RPO ≤ 24 小时、RTO ≤ 2 小时。服务器内恢复与整机丢失恢复分别记录。部署前按批次确认备份、迁移和兼容回退；旧调度不了解新资源规则时，回退先暂停新任务领取。
- **环境。** 旧服务器已停止。当前复用本机 D 盘隔离环境进行轻量验收，正式环境继续使用 PostgreSQL。各阶段记录实际通过的场景与限制；GPU 节点、供应商调用和备份按已授权范围执行。
